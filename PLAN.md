# Табель / График работы — согласованный план (v3)

Дата согласования: 2026-08-29
Статус: план согласован, расчёт ЗП сознательно отложен на 2-й этап (см. ниже) — на старт разработки не влияет.

## Точки (филиалы)

| Точка | Часы работы по умолчанию |
|---|---|
| Ноокат | 09:00–19:00, ежедневно |
| Максом | 10:00–22:00, ежедневно |
| Тынчтык | 10:00–19:00, ежедневно |

Управление точками (создание/редактирование адреса, названия, часов работы по умолчанию/удаление) — доступно **только Владельцу**. Управляющая и сотрудники точки только видят.

## Роли и права доступа

Владелец **не работает по графику вообще** — у неё только управленческие права (контроль, утверждение, администрирование), в самом графике смен/визитов она не фигурирует как исполнитель.

| Действие | Владелец | Управляющая | Сотрудник |
|---|---|---|---|
| Создание/редактирование/удаление точек (филиалов) | ✅ | ❌ | ❌ |
| Создание/редактирование сотрудников | ✅ | ✅ | ❌ |
| Составление черновика графика на неделю | ✅ | ✅ | ❌ |
| Утверждение графика (финальное) | ✅ | ❌ (только черновик) | ❌ (график публикуется без подтверждения сотрудника — решили не усложнять для команды из 5 человек) |
| Просмотр графика (кто/где/когда работает — все точки, все сотрудники) | ✅ | ✅ | ✅ (общий график виден всем) |
| Наличие своих смен/задач в графике | ❌ (не работает по графику) | ✅ (тоже работает как сотрудник) | ✅ |
| Отметка "я на месте" / "я ухожу" (для обычных смен) | ❌ | ✅ | ✅ |
| Отметка "посетила точку" (для визит-задач, см. ниже) | ❌ | — | ✅ |
| Детальный табель/статистика по всем сотрудникам (опоздания, часы, пропуски) | ✅ | ✅ | ❌ (видит только свою личную статистику) |
| Экспорт/просмотр Google-таблицы, расчёт ЗП | ✅ | ✅ | ❌ |
| Управление ролями и доступами пользователей | ✅ | ❌ | ❌ |

Управляющая — тоже сотрудник, значит её аккаунт одновременно имеет роль "управляющая" и участвует в графике как рядовой работник (просто пользователь с расширенным набором прав, отдельную сущность заводить не нужно). Владелец, в отличие от управляющей, в графике не участвует — это чисто контролирующая роль над всей системой.

## Два типа задач в графике

Система различает два типа записей в графике одного сотрудника:

1. **Обычная смена (SHIFT)** — привязана к точке и времени: плановое начало/конец, две отметки факта ("я на месте" / "я ухожу"), опоздания/переработки считаются от времени. Это для продавцов на точках и для управляющей.
2. **Визит-задача (VISIT)** — для сотрудников без фиксированных часов (например, **СММ-специалист**, снимающий контент). Управляющая/владелец назначают только точку и дату ("нужно быть в Максоме такого-то числа"), без плановых часов начала/конца — неважно, во сколько сотрудник придёт и сколько там пробудет. Подтверждение — одна кнопка **"Посетила точку"** (без пары приход/уход), просто фиксирует факт визита с меткой времени для истории. В общий график и в WhatsApp-уведомление это тоже попадает ("Айгуль (СММ) посетила Максом для съёмки контента"), чтобы владелец/управляющая видели, что визит состоялся.

Оба типа задач проходят один и тот же цикл согласования графика (черновик → апрув владельца → публикация) — просто у VISIT нет полей времени. Владелец в обоих случаях только утверждает график и смотрит статистику, но сама в графике не значится.

## Процесс составления графика

Изучили, как это устроено в популярных сервисах учёта смен (7shifts, Homebase, When I Work, Deputy, Connecteam) — почти никто не требует от сотрудника подтверждать каждую смену перед публикацией: график просто становится видимым сразу после публикации. Решили сделать так же — для команды из 5 человек обязательное подтверждение только создавало путаницу, не добавляя пользы.

1. **Черновик** — управляющая (или владелец) распределяет смены/визит-задачи на следующую неделю, по умолчанию подставляются стандартные часы точки (для SHIFT). Черновик может создавать и редактировать и владелец, и управляющая.
2. **На утверждении у владельца** — только если черновик создала управляющая: владелец видит график по всем точкам, утверждает целиком или возвращает на доработку с комментарием. Если черновик создал сам владелец, этот шаг пропускается — публикация сразу.
3. **Опубликован** — график сразу виден всем сотрудникам, без подтверждения с их стороны; становится основой для сверки отметок. Правки опубликованного графика применяются сразу же.

### Срочные изменения в течение недели (согласовано)

Правки уже опубликованного графика (болезнь, замена и т.д.) не гоняются через полный цикл заново:
- Управляющая правит опубликованный график.
- Уведомляются только затронутые сотрудники + владелец (для контроля).
- Все изменения логируются в историю графика (кто, когда, что поменял) — на случай споров.

## Ежедневная отметка и табель (согласовано: приход + уход для SHIFT)

Сотрудник на обычной смене жмёт две кнопки:
- **"Я на месте"** — фиксируется точное время прихода, сверяется с плановым временем начала смены (вовремя/опоздание на N минут).
- **"Я ухожу"** — фиксируется точное время ухода, сверяется с плановым временем окончания смены (пораньше/переработка).

Сотрудник на визит-задаче (СММ) жмёт одну кнопку "Посетила точку" (см. выше).

Владелец таких отметок не делает — она не работает по графику, только наблюдает.

Все отметки уходят уведомлением в общий чат WhatsApp ("Айгуль вышла на работу в Ноокат, 09:03" / "Айгуль ушла с работы, 19:05" / "Айгуль посетила Максом для съёмки контента, 14:20").

### WhatsApp-интеграция (техническое решение)

Официальный WhatsApp Business API групповые чаты не поддерживает в принципе. Рабочий вариант: отдельный номер (физическая SIM/eSIM), добавленный в общий чат как участник, подключённый к серверу через **Baileys** (бесплатная open-source библиотека, протокол WhatsApp Multi-Device, без эмуляции браузера). Один раз сканируется QR-код — дальше сессия держится сама, сервер шлёт сообщения в группу программно.
Риск временной блокировки номера низкий при таком объёме сообщений (5 сотрудников, пара сообщений в день), но канал уведомлений закладывается как заменяемый модуль — если WhatsApp станет проблемным, можно быстро переключиться на Telegram-группу (официальный Bot API, без рисков блокировки).

## Табель и Google-таблица (согласовано: ежедневная выгрузка)

Каждое утро (например, 07:00 по Бишкеку) автоматическая задача выгружает в Google-таблицу данные табеля за **вчера**: точка, сотрудник, тип задачи (смена/визит), плановое время (если есть), фактический приход/уход или факт визита, опоздание/переработка.
Структура таблицы:
- Лист **"Табель"** — построчная ежедневная выгрузка (append, накопительно).
- Лист **"Итоги за месяц"** — автоматические формулы (SUMIFS/COUNTIFS) считают по каждому сотруднику итоговые дни/часы за текущий месяц на основе листа "Табель" — отдельная ручная выгрузка в конце месяца не нужна, всё уже накоплено.

Владелец в этих отчётах не фигурирует как исполнитель (только как читатель отчётов).

## Расчёт ЗП — отложено на 2-й этап

Пользователь решил не привязывать сейчас правила расчёта зарплаты (оклад/ставка за смену/ставка за час, премии/штрафы) — вернёмся к этому вопросу отдельно, когда дойдём до соответствующего этапа. На 1-м этапе система просто копит фактические данные табеля (дни/часы/визиты), которых достаточно, чтобы посчитать ЗП вручную в таблице уже сейчас, а автоматизацию расчёта добавим позже.

## Мобильное приложение vs адаптивный сайт (PWA)

Рекомендация: **не** делать нативное приложение (отдельная разработка под iOS и Android, публикация в App Store/Google Play, поддержка двух кодовых баз) — это неоправданно дорого и долго для внутреннего инструмента на 5 пользователей.
Вместо этого — **PWA (Progressive Web App)**: адаптивный сайт, который на телефоне можно "добавить на главный экран" — тогда он открывается как отдельное приложение, без адресной строки браузера, со своей иконкой, может работать даже при слабом интернете (кэширование). Разработка и обновления — в разы быстрее и дешевле, работает одинаково на Android и iPhone, обновляется мгновенно без проверки в сторах.

## Технологический стек (рекомендация)

- **Next.js** (React) — фронтенд и backend-логика в одном проекте.
- **PostgreSQL** через Supabase или Neon — там же удобно сделать логин/пароль и роли.
- **Хостинг** — Vercel.
- **WhatsApp-бот (Baileys)** — отдельный постоянно работающий Node-процесс на Railway или Fly.io.
- **Google Sheets API** через сервисный аккаунт — для ежедневной автовыгрузки.

Ориентировочные расходы на инфраструктуру: 0–10$/мес.

## Основные сущности данных

- **Points** (точки): id, название, адрес, часы работы по умолчанию, активна/нет.
- **Users**: id, имя, телефон, логин, пароль (хэш), роль (owner/manager/employee), активен/нет. У owner нет связанных Shifts.
- **Schedules** (графики): неделя, статус (draft/pending_owner/published), кем создан.
- **Shifts** (смены/задачи): schedule_id, point_id, user_id (никогда не owner), тип (SHIFT/VISIT), план. начало, план. конец (пусто для VISIT).
- **Attendance** (факт по табелю): shift_id, факт. приход, факт. уход (для SHIFT) или факт. визита (для VISIT), статус (вовремя/опоздание/переработка — только для SHIFT).
- **ScheduleChangeLog**: история правок опубликованного графика (кто/когда/что).
