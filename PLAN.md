# Табель / График работы — согласованный план (v4)

Дата согласования: 2026-09-01
Статус: план согласован, расчёт ЗП сознательно отложен на 2-й этап (см. ниже) — на старт разработки не влияет.

**v4 меняет то, что было решено в v3** — по итогам реального использования на
телефоне через Vercel-деплой владелец переиграл несколько решений: подтверждение
сотрудниками (уже было убрано в v3) остаётся убранным; но владелец и управляющая
теперь **могут работать по графику как подмена**; график — **один общий на всех**
(без отдельного личного вида); строки — точки, а не сотрудники; время нигде в
графике не показывается; появилось жёсткое правило "обязательный сотрудник на
каждой точке каждый день"; текущая и следующая неделя показываются вместе на
одной странице.

## Точки (филиалы)

| Точка | Часы работы по умолчанию |
|---|---|
| Ноокат | 09:00–19:00, ежедневно |
| Максом | 10:00–22:00, ежедневно |
| Тынчтык | 10:00–19:00, ежедневно |

Управление точками (создание/редактирование адреса, названия, часов работы по умолчанию/удаление) — доступно **только Владельцу**. Управляющая и сотрудники точки только видят.

## Роли и права доступа

И владелец, и управляющая теперь могут быть назначены на график **как подмена**
(обычная смена или визит-задача) — например, если заболел сотрудник. Это не
основная их роль, но система больше не запрещает это на уровне сервера.
Управляющих может быть несколько; создать или назначить роль "управляющая"
может только владелец (у управляющей в форме добавления сотрудника роль вообще
не выбирается — любой её новый сотрудник заводится рядовым).

| Действие | Владелец | Управляющая | Сотрудник |
|---|---|---|---|
| Создание/редактирование/удаление точек (филиалов) | ✅ | ❌ | ❌ |
| Создание/редактирование сотрудников | ✅ | ✅ (только рядовых, роль не меняет) | ❌ |
| Назначение/смена роли "управляющая" | ✅ (только владелец) | ❌ | ❌ |
| Составление черновика графика на неделю | ✅ | ✅ | ❌ |
| Утверждение графика (финальное) | ✅ | ❌ (только черновик → на утверждение) | ❌ (график публикуется без подтверждения сотрудника) |
| Просмотр графика (все точки, все сотрудники, единая сетка) | ✅ | ✅ | ✅ |
| Быть назначенным на смену/визит как подмена | ✅ | ✅ | ✅ |
| Отметка "я на месте" / "я ухожу" (для обычных смен) | ✅ (если назначен) | ✅ | ✅ |
| Отметка "посетила точку" (для визит-задач, см. ниже) | ✅ (если назначен) | ✅ | ✅ |
| Детальный табель/статистика по всем сотрудникам (опоздания, часы, пропуски) | ✅ | ✅ | ❌ (видит только свою личную статистику) |
| Экспорт/просмотр Google-таблицы, расчёт ЗП | ✅ | ✅ | ❌ |
| Управление ролями и доступами пользователей | ✅ | ❌ | ❌ |

## Два типа задач в графике

Система различает два типа записей в графике одного сотрудника:

1. **Обычная смена (SHIFT)** — привязана к точке и времени: плановое начало/конец, две отметки факта ("я на месте" / "я ухожу"), опоздания/переработки считаются от времени. Это для продавцов на точках и для управляющей.
2. **Визит-задача (VISIT)** — для сотрудников без фиксированных часов (например, **СММ-специалист**, снимающий контент). Управляющая/владелец назначают только точку и дату ("нужно быть в Максоме такого-то числа"), без плановых часов начала/конца — неважно, во сколько сотрудник придёт и сколько там пробудет. Подтверждение — одна кнопка **"Посетила точку"** (без пары приход/уход), просто фиксирует факт визита с меткой времени для истории. В общий график и в WhatsApp-уведомление это тоже попадает ("Айгуль (СММ) посетила Максом для съёмки контента"), чтобы владелец/управляющая видели, что визит состоялся.

Оба типа задач проходят один и тот же цикл согласования графика (черновик → апрув владельца → публикация) — просто у VISIT нет полей времени. Время (плановое начало/конец SHIFT) в интерфейсе графика **нигде не показывается и не вводится вручную** — оно молча подставляется из стандартных часов работы точки и используется только для расчёта опозданий/переработок в Табеле. Владелец в обоих случаях так же может выступать исполнителем как подмена (см. выше).

## Обязательный сотрудник на каждой точке (жёсткое правило)

На каждой активной точке в каждый день недели должна быть назначена хотя бы
одна обычная смена (SHIFT) — визит-задача (VISIT) в счёт не идёт. Пока это не
так, отправить график на утверждение владельцу (или опубликовать, если черновик
владельца) нельзя — кнопка вообще не показывается, вместо неё предупреждение
с количеством незакрытых точек/дней. В самой сетке такие ячейки подсвечены
жёлтым с "!". Проверка дублируется на сервере (и при отправке, и при
утверждении), чтобы её нельзя было обойти.

## Процесс составления графика

Изучили, как это устроено в популярных сервисах учёта смен (7shifts, Homebase, When I Work, Deputy, Connecteam) — почти никто не требует от сотрудника подтверждать каждую смену перед публикацией: график просто становится видимым сразу после публикации. Решили сделать так же — для команды из 5 человек обязательное подтверждение только создавало путаницу, не добавляя пользы.

1. **Черновик** — управляющая (или владелец) распределяет смены/визит-задачи на неделю прямо в общей сетке (тап по ячейке точка×день → список назначенных + добавление). Черновик может создавать и редактировать и владелец, и управляющая; текущая и следующая неделя редактируются независимо (следующую можно готовить заранее, как черновик — она не обязана быть готова заранее срока, но должна быть утверждена/опубликована до того, как станет текущей).
2. **На утверждении у владельца** — только если черновик создала управляющая, и только когда на каждой точке/дне есть обязательный сотрудник: владелец видит график по всем точкам, утверждает целиком или возвращает на доработку с комментарием. Если черновик создал сам владелец, этот шаг пропускается — публикация сразу.
3. **Опубликован** — график сразу виден всем сотрудникам, без подтверждения с их стороны; становится основой для сверки отметок. Правки опубликованного графика применяются сразу же.

### Единая сетка графика (согласовано по итогам живого использования)

Сетка — **одна общая для всех ролей** (не отдельный личный вид для сотрудника):
каждая точка — своя секция на всю ширину экрана (имя точки сверху, под ним
7 ячеек-дней в ряд, без отдельной колонки под название точки — это отъедало
ширину и на реальном iPhone делало аватарки слишком мелкими для тапа).
Внутри ячейки — компактные цветные кружки-аватарки участников (без
имени/времени текстом, чтобы неделя целиком помещалась на экран телефона без
горизонтальной прокрутки): круглая — обязательная смена (SHIFT, показывается
первой), скруглённый квадрат со значком-булавкой в углу — визит (VISIT,
вторым; раньше был серый пунктирный контур, но он читался как "ждёт
подтверждения", поэтому заменён на полноценную заливку цветом сотрудника +
свою узнаваемую форму). Тап по ячейке открывает окно снизу со списком
назначенных, кнопкой отметки "я на месте"/"я ухожу"/"посетила точку" (для
своей смены сегодня, кнопки укрупнены и окно приподнято над нижним краем
экрана — на iPhone в Safari нижняя панель браузера перекрывала мелкие
кнопки) и, для владельца/управляющей, добавлением/снятием сотрудника — это
же и есть способ поправить уже опубликованный график: тап по ячейке работает
одинаково для черновика и для опубликованной недели, разницы для
владельца/управляющей нет. Сегодняшний день подсвечен, у владельца/управляющей
в шапке на аватаре загорается красная точка, если что-то требует их внимания
(черновик ждёт утверждения, или не хватает обязательного сотрудника). Текущая
и следующая неделя показаны друг под другом на одной странице; прошлые (и
дальше будущие) недели — через отдельную ссылку, в режиме только чтения.

### Срочные изменения в течение недели (согласовано)

Правки уже опубликованного графика (болезнь, замена и т.д.) не гоняются через полный цикл заново:
- Управляющая правит опубликованный график.
- Уведомляются только затронутые сотрудники + владелец (для контроля).
- Все изменения логируются в историю графика (кто, когда, что поменял) — на случай споров.

## Ежедневная отметка и табель (согласовано: приход + уход для SHIFT)

Сотрудник на обычной смене жмёт две кнопки:
- **"Я на месте"** — фиксируется точное время прихода, сверяется с плановым временем начала смены (вовремя/опоздание на N минут).
- **"Я ухожу"** — фиксируется точное время ухода, сверяется с плановым временем окончания смены (пораньше/переработка).

Сотрудник на визит-задаче (СММ) жмёт одну кнопку "Посетила точку" (см. выше).

Те же кнопки доступны владельцу и управляющей, если они сами назначены на
смену/визит как подмена — правила отметки для них ровно те же, что и для
рядового сотрудника.

Все отметки уходят уведомлением в общий чат WhatsApp ("Айгуль вышла на работу в Ноокат, 09:03" / "Айгуль ушла с работы, 19:05" / "Айгуль посетила Максом для съёмки контента, 14:20").

### WhatsApp-интеграция (техническое решение)

Официальный WhatsApp Business API групповые чаты не поддерживает в принципе. Рабочий вариант: отдельный номер (физическая SIM/eSIM), добавленный в общий чат как участник, подключённый к серверу через **Baileys** (бесплатная open-source библиотека, протокол WhatsApp Multi-Device, без эмуляции браузера). Один раз сканируется QR-код — дальше сессия держится сама, сервер шлёт сообщения в группу программно.
Риск временной блокировки номера низкий при таком объёме сообщений (5 сотрудников, пара сообщений в день), но канал уведомлений закладывается как заменяемый модуль — если WhatsApp станет проблемным, можно быстро переключиться на Telegram-группу (официальный Bot API, без рисков блокировки).

## Табель и Google-таблица (согласовано: ежедневная выгрузка)

Каждое утро (например, 07:00 по Бишкеку) автоматическая задача выгружает в Google-таблицу данные табеля за **вчера**: точка, сотрудник, тип задачи (смена/визит), плановое время (если есть), фактический приход/уход или факт визита, опоздание/переработка.
Структура таблицы:
- Лист **"Табель"** — построчная ежедневная выгрузка (append, накопительно).
- Лист **"Итоги за месяц"** — автоматические формулы (SUMIFS/COUNTIFS) считают по каждому сотруднику итоговые дни/часы за текущий месяц на основе листа "Табель" — отдельная ручная выгрузка в конце месяца не нужна, всё уже накоплено.

Владелец в этих отчётах не фигурирует как исполнитель (только как читатель отчётов).

## Расчёт ЗП — отложено на 2-й этап

Пользователь решил не привязывать сейчас правила расчёта зарплаты (оклад/ставка за смену/ставка за час, премии/штрафы) — вернёмся к этому вопросу отдельно, когда дойдём до соответствующего этапа. На 1-м этапе система просто копит фактические данные табеля (дни/часы/визиты), которых достаточно, чтобы посчитать ЗП вручную в таблице уже сейчас, а автоматизацию расчёта добавим позже.

## Мобильное приложение vs адаптивный сайт (PWA) — реализовано

Решили **не** делать нативное приложение (отдельная разработка под iOS и Android, публикация в App Store/Google Play, поддержка двух кодовых баз) — это неоправданно дорого и долго для внутреннего инструмента на 5 пользователей.
Вместо этого сделали **PWA (Progressive Web App)**: сайт добавляется на главный экран телефона и открывается как отдельное приложение, без адресной строки браузера, со своей иконкой (`src/app/manifest.ts`). Нижняя таб-панель (График/Табель) на телефоне вместо верхнего меню — тоже часть этого решения; управление (Сотрудники/Точки) для владельца и управляющей теперь открывается тапом по профилю в шапке.

## Фирменный стиль (согласовано: по реальному логотипу AYAY KYZ)

Владелец прислал готовый логотип компании (круглая акварельная иллюстрация
двух девушек в кыргызском и современном образе, с маками и белым цветком) и
делегировал дизайн-решения целиком. На его основе:
- Фирменный акцентный цвет — тёплая терракота, снятая прямо с короны на
  логотипе (`#c8400e`), заменил собой индиго по всему интерфейсу (кнопки,
  ссылки, активные вкладки, кольцо "это я" на аватарке, полоса статус-бара
  и PWA-манифест). Палитра для UI-состояний (hover/фон/т.д.) посчитана из
  этого же цвета.
- Заголовки и логотип-текст — гарнитура **Lora** (тёплая антиква, с
  поддержкой кириллицы), обычный текст и таблицы остаются на системном
  sans-serif ради читаемости данных. Шрифт хранится прямо в проекте
  (`src/fonts/lora`), а не грузится с Google Fonts при сборке.
- Сам логотип вставлен в шапку приложения (рядом с названием) и на страницу
  входа; из него же собраны все иконки PWA/favicon.

## Технологический стек (рекомендация)

- **Next.js** (React) — фронтенд и backend-логика в одном проекте.
- **PostgreSQL** через Supabase или Neon — там же удобно сделать логин/пароль и роли.
- **Хостинг** — Vercel.
- **WhatsApp-бот (Baileys)** — отдельный постоянно работающий Node-процесс на Railway или Fly.io.
- **Google Sheets API** через сервисный аккаунт — для ежедневной автовыгрузки.

Ориентировочные расходы на инфраструктуру: 0–10$/мес.

## Основные сущности данных

- **Points** (точки): id, название, адрес, часы работы по умолчанию, активна/нет.
- **Users**: id, имя, телефон, логин, пароль (хэш), роль (owner/manager/employee), активен/нет. Owner тоже может иметь связанные Shifts (как подмена).
- **Schedules** (графики): неделя, статус (draft/pending_owner/published), кем создан.
- **Shifts** (смены/задачи): schedule_id, point_id, user_id (любая активная роль), тип (SHIFT/VISIT), план. начало, план. конец (пусто для VISIT; для SHIFT подставляются из часов точки и не редактируются вручную в интерфейсе графика).
- **Attendance** (факт по табелю): shift_id, факт. приход, факт. уход (для SHIFT) или факт. визита (для VISIT), статус (вовремя/опоздание/переработка — только для SHIFT).
- **ScheduleChangeLog**: история правок опубликованного графика (кто/когда/что).

## Роадмап

- **Этап 0 (пройден)** — согласование плана.
- **Этап 1 — MVP (реализовано)**: роли и логин/пароль, точки (CRUD владельца), сотрудники, график с двумя типами задач (SHIFT/VISIT), кнопки прихода/ухода и "посетила точку", табель внутри системы, полный цикл согласования графика и правки опубликованного графика.
- **Этап 2 (частично реализовано)**: цикл утверждения графика — готово; PWA, единая сетка точки×дни, обязательный сотрудник на точку/день, владелец/управляющая как подмена, профиль с индикатором внимания — готово. Осталось: реальные WhatsApp-уведомления об утверждении графика (отметки прихода/ухода/визита уже уведомляют — заглушка в `src/lib/notify.ts`, готова к подключению Baileys-бота).
- **Этап 3**: автовыгрузка в Google Sheets (сейчас — CSV-экспорт по кнопке как промежуточный вариант), лист "Итоги за месяц", расчёт ЗП (правила будут определены отдельно перед этим этапом).
- **Этап 4 (опционально)**: формальные заявки на отгул/больничный с апрувом, push-уведомления, редактирование графика дальше, чем на неделю вперёд (сейчас дальние недели доступны только для просмотра).
